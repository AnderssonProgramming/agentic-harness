# Plan: B-08 Conversation survives closing the app

Status: approved by the Product Owner on 2026-10-01, as written, with decisions 1–6 as proposed.
Sources read: `CLAUDE.md`, `CONTEXT-ROUTINE.md`, `BACKLOG.md` (B-08 only), `ARCHITECTURE.md` (Decision index, ADR-04, ADR-07), `src/features/chat/` (`model/message.ts`, `hooks/use-chat.ts`, `api/chat-api.ts`, `components/chat-screen.tsx`), `scripts/lib/chrome.mjs` (`openChrome`), `server/llm/engines/mock.ts` (the `[mock:slow]` hook).

## Scope

- In: every B-08 criterion. The conversation is saved in the browser's `localStorage`, under one key, as a versioned JSON snapshot.
- Out: more than one conversation, or a conversation list (no backlog item asks for it). Syncing across devices or a server-side store. The team's documents (B-06).
- No new dependencies. Validation of stored data is a hand-written type guard, not a schema library.

## Design in short

| Layer                                         | Responsibility                                                                                                                                                                                                                                                                                                                                                        |
| --------------------------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `model/conversation-snapshot.ts` (pure)       | `toSnapshot(messages)` builds `{ version: 1, messages }`. `restoreSnapshot(raw, migrations)` parses, migrates known older versions, validates every message, and turns any `streaming` reply into `stopped` with its partial text. Returns `{ messages, outcome: 'restored' \| 'empty' \| 'reset' }`, where `reset` means the data was unreadable and was discarded.  |
| `model/message.ts` (pure)                     | `canClear(messages)`: the one validation that both disables "New conversation" and guards its handler.                                                                                                                                                                                                                                                                |
| `api/conversation-store.ts` (the only access) | `load()`, `save(messages)`, `clear()` over an injected `Storage` getter (the browser's `localStorage` by default). Every exception (`SecurityError` when storage is blocked, `QuotaExceededError` when it's full) becomes a typed result `{ ok: false, reason: 'unavailable' \| 'full' }`, never a throw. Unreadable data is removed so the notice appears only once. |
| `hooks/use-chat.ts`                           | Restores on first render. Saves after every change: immediately for status changes (sent, finished, stopped, failed, retried, cleared), and at most once a second for streamed text, plus a flush on `pagehide`. Adds `clear()` (aborts any reply in progress, then empties memory and storage) and `storageNotice`.                                                  |
| `components/`                                 | `StorageNotice` (`role="status"`) and `NewConversation` (button plus an inline "Clear this conversation? Clear / Cancel" confirmation; the open/closed toggle is its only state, as CLAUDE.md allows). `ChatScreen` stays the only caller of `useChat`.                                                                                                               |

## Decisions for the PO to review

1. **Synchronous storage API.** ADR-07 says `api/` exports async functions. `localStorage` is synchronous, and a synchronous `load()` lets `useChat` restore inside its `useState` initializer, with no empty-then-filled flash and no loading state. I propose a synchronous `api/conversation-store.ts`, recorded in ADR-10 as a refinement of ADR-07 (the boundary stays the same; only the return type isn't a `Promise`).
2. **"Older format" when there is none yet.** B-08 is the first time anything is saved, so no older format exists in the wild. I propose: the snapshot is `version: 1`; `restoreSnapshot` takes the migrations table as a parameter (empty in production); the migration test passes a fixture `0 → 1` migration to prove the path works. Unknown and future versions give `reset`. The alternative is to invent a real version 0, which I don't recommend: it would be code for data that never existed.
3. **Inline confirmation, not `window.confirm`.** It keeps the component a pure function of props plus one toggle, is testable with Testing Library, and doesn't block the page while a reply streams.
4. **Save cadence.** Every status change is written at once; streamed text at most once a second plus on `pagehide`. Writing on every token would rewrite the whole conversation dozens of times a second. The cost: if the browser crashes (not a normal close), up to one second of streamed text can be lost; the reply still comes back `stopped`.
5. **ESLint guard (step 4).** It's a config change, so it needs your approval. It adds a rule; it doesn't disable one. Without it, "Boundaries" is only covered by review.
6. **CLAUDE.md "Current state".** It says conversations aren't saved across reloads. That line will be wrong after step 8. Since CLAUDE.md changes go in their own commit, I'll propose that edit separately at the end, not inside these steps.

## Risks

- Chrome may hold `localStorage` in memory for a moment before writing it to disk. A forced kill could make scenario (a) flaky; that's why step 7 closes with `Browser.close` and waits for the process to exit before reopening the profile.
- `QuotaExceededError` and `SecurityError` are `DOMException`s, with different names across browsers. The store matches on "any exception from storage", and keeps `name` only to choose between "unavailable" and "full" in the notice.
